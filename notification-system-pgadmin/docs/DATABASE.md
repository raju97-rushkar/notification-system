# Database Design (PostgreSQL)

There are three tables: `reminders`, `notifications`, `failed_attempts`. They are all defined in [src/db/schema.sql](../src/db/schema.sql), which runs on every app start. Because it uses `CREATE TABLE IF NOT EXISTS`, running it again changes nothing.

## 1. reminders

| Column | Type | Meaning |
|---|---|---|
| `id` | UUID | primary key, generated by PostgreSQL (`gen_random_uuid()`) |
| `user_id` | TEXT | owner |
| `title`, `message` | TEXT | content |
| `due_at` | TIMESTAMPTZ | when it should fire (stored as UTC) |
| `timezone` | TEXT | user's timezone, only used for `dueAtLocal` |
| `status` | TEXT + `CHECK` | only `pending`, `processing`, `completed`, `failed`, `cancelled` are allowed |
| `next_run_at` | TIMESTAMPTZ | when the worker should pick it up. Equal to `due_at` at first, moved later after a failure |
| `attempts`, `max_attempts` | INTEGER | tries so far / allowed |
| `last_error` | TEXT | message of the last error |
| `locked_by`, `locked_until` | TEXT, TIMESTAMPTZ | which worker is processing it, and until when |
| `processed_at`, `created_at`, `updated_at` | TIMESTAMPTZ | timestamps |

**Why `TIMESTAMPTZ` and not `TIMESTAMP`?** `TIMESTAMPTZ` stores an exact moment in UTC. `2026-12-01T10:00:00+05:30` and `2026-12-01T04:30:00Z` are saved as the same value. A plain `TIMESTAMP` has no timezone, so the same text could mean different moments on different servers.

**Why a `CHECK` on status?** The database itself refuses an invalid status, even if there is a bug in our code.

### Indexes

| Index | Columns | Used by |
|---|---|---|
| `idx_reminders_status_next_run` | `(status, next_run_at)` | worker: pending reminders whose time has come |
| `idx_reminders_status_locked_until` | `(status, locked_until)` | worker: stuck reminders whose lock expired |
| `idx_reminders_user_status_due` | `(user_id, status, due_at)` | API: my reminders, filter by status, sort by date |
| `idx_reminders_user_created` | `(user_id, created_at DESC)` | API: my reminders, newest first |

**How the order of columns was chosen:** columns compared with `=` come first (`status`, `user_id`). The column used for sorting or ranges (`<=`, `>=`) comes last. With this order PostgreSQL can jump straight to the right rows, already sorted, instead of reading the whole table.

You can check that an index is used in pgAdmin's Query Tool:
```sql
EXPLAIN SELECT * FROM reminders WHERE status = 'pending' AND next_run_at <= now() ORDER BY next_run_at LIMIT 1;
```
With a small table PostgreSQL may still choose a `Seq Scan`, because reading 10 rows directly is faster than using an index. With many rows it switches to an `Index Scan`.

## 2. notifications

| Column | Meaning |
|---|---|
| `reminder_id` | **UNIQUE** + foreign key to `reminders(id)` |
| `user_id`, `title`, `message` | copied from the reminder, so listing notifications needs no JOIN |
| `scheduled_for` | the reminder's `due_at` |
| `delay_ms` | BIGINT, how late it was created |
| `read_at` | `NULL` = unread |

**`UNIQUE (reminder_id)` is the most important rule in the design.** PostgreSQL itself refuses a second notification for the same reminder, even if two workers try at exactly the same moment. We insert with `ON CONFLICT (reminder_id) DO NOTHING`: if a notification already exists, nothing is inserted and no error is thrown.

A check in our own code ("SELECT, then INSERT if missing") would not be safe. Two workers can both run the SELECT before either one inserts.

**Foreign key with `ON DELETE CASCADE`:** a notification always belongs to an existing reminder. If a reminder row is ever deleted, its notifications are deleted too.

Index: `(user_id, created_at DESC)` for "my notifications, newest first".

## 3. failed_attempts

`id, reminder_id (FK), attempt, error, worker_id, will_retry, created_at`, with one row per failed attempt.

| Index | Used by |
|---|---|
| `(reminder_id)` | `GET /reminders/:id/attempts` |
| `(created_at)` | the worker deletes rows older than 30 days |

**Why a separate table?** Each failure is a new row, so the reminder row stays small and fast to update. It's also easy to query, e.g. `SELECT * FROM failed_attempts WHERE created_at > now() - interval '1 hour'`.

PostgreSQL has no TTL index like MongoDB, so the worker runs `DELETE ... WHERE created_at < now() - interval '30 days'` on every run. The `created_at` index makes that cheap.

## 4. Performance and safety decisions

- **Connection pool** (`pg.Pool`, max 10): connections are reused instead of opening one per query.
- **Parameters everywhere** (`$1, $2`): values are never put inside the SQL text. This is what prevents SQL injection, and there is a test for it.
- **Sort column whitelist**: `sortBy` can only be one of `due_at`, `created_at`, `title`, so user text never reaches `ORDER BY`.
- **LIKE escaping**: `%` and `_` in the search text are escaped, so they are not wildcards.
- **Pagination**: the rows query and the `COUNT(*)` query run at the same time (`Promise.all`). `limit` is capped at 100.
- **Worker claim in one statement**: `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *`.
- **Database clock**: the worker uses `now()` from PostgreSQL, not the server's clock, so several servers always agree on what "due" means.
- **Possible improvements for very large data** (not needed at this size): partial indexes such as `WHERE status = 'pending'`, and cursor pagination instead of `OFFSET`.

## 5. Why no transaction around "create notification + mark completed"?

These are two separate statements. We could wrap them in `BEGIN ... COMMIT`, but we don't need to. `UNIQUE` + `ON CONFLICT DO NOTHING` already makes them safe. If the server crashes between the two statements, the next attempt inserts nothing (the notification already exists) and just marks the reminder completed. The user never gets two notifications, and no reminder is lost.

(A transaction *is* used in one place: creating the tables on startup, together with an advisory lock, so two processes starting at the same time don't both run `CREATE TABLE`.)
